# GODMODE — playable prototype demo plan

## The outcome to prove

Ask for a change, then watch real people, travel, needs and finite resources determine what actually happens. The larger pitch is **“The era of finished software is ending.”** The current film must distinguish that ambition from the behavior already implemented.

This is a practical capture/edit plan, not a rendered new video. The earlier 72-second film is preserved and predates this entry, cast and direct composer; do not present it as footage of the current release.

## Separate future Muse section — blocked until real access

After the selected Meta provider has verified access, credit authorization and project budget, record a real request end to end: typed world description → provider-backed blueprint → actual three resident profiles and unsupported requests → explicit Create → separate paused save → Play. Retain the raw provider receipt and created-save lineage.

Only then replace the unavailable opening with this 15–25 second sequence. A subsequent resident thought or plan must come from that resident's own recorded model decision; entering a world prompt is not proof of autonomous resident reasoning. Do not use a fixture, Qwen result, keyword preset, generated concept image or editing trick as a live Muse response. Imported provider claims remain unverified unless independently established.

The current blueprint uses the fixed neighborhood and three NPC slots. It changes supported profiles, values and rules; it does not generate arbitrary terrain, occupations, limitless new mechanics or ten dynamic villagers. Wishes needing missing mechanics remain wishes. Current generated art was prepared separately; world creation does not remotely generate new art.

## Capture and delivery checklist

1. Keep older worlds intact; fork or use a separately named demonstration save. Record each save ID and the action source.
2. Leave Meta unavailable for the current offline cut. No new provider request, purchase, credential change, deployment or final submission is needed to capture it.
3. Capture at 1920×1080 if practical; use native pixelated art rendering and readable UI scale. Close developer panels during ordinary play. Include diagnostics only in a separate technical appendix.
4. Preserve real pauses, refusals and failures. Compress travel with an explicit time-edit label. Do not modify needs or consent offscreen to force a preferred ending.
5. Keep current source HTML/UI capture, input recording, exact replay result, provider provenance (if any), asset manifest, edit decision list and final encode metadata together. No music or voice service is required; silent captions or original human narration are sufficient.
6. Review decoded start/middle/end frames and a motion contact sheet after rendering. Verify duration, H.264 dimensions and playback. This plan does not claim that a new MP4 has been rendered.
7. Check the organizer's final video, repository and eligibility requirements before any official submission. The application is received/Pending; this demo plan does not establish admission or pre-event-work eligibility.
